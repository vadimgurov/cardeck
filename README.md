# CarDeck — пусть ваш телефон Android действует как iPhone, подключенный напрямую к вашему автомобилю

Пусть обычный телефон Android (не рутированный) выступает в роли **отправителя CarPlay (роль iPhone)**,
Спроецируйте нарисованный интерфейс приложения на автомобиль, поддерживающий CarPlay.

> **Неофициальный проект**: Этот проект представляет собой личную экспериментальную работу и не имеет никакого отношения к Apple Inc. или какому-либо производителю автомобилей.
> Не авторизовано и не сертифицировано и **не является продуктом MFi**. CarPlay/AirPlay являются товарными знаками Apple Inc.
> Появляется в тексте только для иллюстрации целей совместимости.
>
> **Безопасность вождения**: настройка и работа ограничиваются парковкой; отключение во время вождения может привести к сбою навигации, используйте оригинальную навигацию в качестве резервной системы безопасности.
>
> Полные положения и условия можно найти по адресу [ОТКАЗ ОТ ОТВЕТСТВЕННОСТИ.md](DISCLAIMER.md) (тот же источник, что и заявление об отказе от ответственности при первом запуске приложения).

## Сначала вывод (технико-экономическое обоснование)

- **Направление противоположно DiPlay/xcertplay**: они являются принимающей стороной (роли автомобиля и машины); этот проект является отправной точкой.
  **DiPlay — это производная от xcertplay, а также фактический тестовый стенд, используемый в этом проекте**; `reference/`
  Исходные коды обоих зарезервированы для справки (знания о протоколах используются на уровне iAP2/канального уровня/Bonjour, а логика ролей не включает друг друга).
- **Отправителю не требуется подпись Apple**: аутентификация iAP2 является односторонней (телефон проверяет сертификат MFi автомобиля,
  Автомобиль и машина доверяют результатам, сообщаемым пользователем мобильного телефона, что было публично подтверждено Oligo Security DEF CON 2025).
- **Проводной USB-маршрут исключен** (приложение не может управлять USB-гаджетом, Honor не может разблокировать BL),
  Используйте только беспроводную связь: Bluetooth RFCOMM → Автомобильная точка доступа → mDNS → iAP2/AirPlay.
- Подробную основу протокола можно найти по адресу [docs/PROTOCOL-NOTES.md](docs/PROTOCOL-NOTES.md).

**Все этапы 3-C (11 октября 2026 г., фактическая приемка автомобиля Audi)**: iAP2 → Сопряжение с AirPlay → Потоковое видео →
Touch Backhaul → Виртуальный экран добавляется в полную ссылку, и с ним можно взаимодействовать. Результаты сегодняшней атаки (подробнее см. `docs/PROTOCOL-NOTES.md` §9c):

1. **Случай сопряжения AirPlay 403**: в запросе на сопряжение отсутствует заголовок логотипа Apple (`Content-Type: application/pairing+tlv8` +
   `X-Apple-HKP: 2`, проверка пары плюс `X-Apple-PD: 1`, сравнение кошачьей игры PairingHelperTx дословно).
   После завершения настройки пары/проверки пары — все 200, и машина сохраняет долгосрочный открытый ключ.
2. **Случай потока экрана 400**: программа SETUP должна объявить **настоящий порт синхронизации UDP** (TimingServer, ответ RTCP NTP).
   И функции отправляют **полный список возможностей iPhone** (получающая сторона нажимает «Поддержка автомобиля ∩ Предложение по мобильному телефону», чтобы рассчитать пересечение,
   Только упоминание videoPlayback получит пустой набор → видеоконвейер не включен); Объявление ресурса modeChanged идет первым;
   UA/sourceVersion использует значение, сообщенное самим iPhone (566.25.21), не используйте значение телефона.
3. **Сеанс 10 секунд, чтобы разорвать соединение и решить проблему**: Двойной контрольный сигнал необходим — пинг KeepAlive UDP (автомобильный компьютер KeepAlivePort, цикл 10 секунд)
   + `POST /feedback` (период 1 с, кошачья игра FEEDBACK_INTERVAL).
4. **Touch Link (последнее на сегодня поле боя, пять поражений подряд)**:
   - Команды автомобиля и машины должны проходить через `POST /command` в **сокете канала событий** (режим «выстрелил и забыл», независимый CSeq,
     Ключ событий), отправляется по управляющему соединению RTSP и не может быть получен автомобилем (свидетельство DiPlay sendCommandLocked)
   - `hidSetInputMode` (строка uuid возвращается как есть) Автомобиль-автомат начинает отправлять касания только после постановки на охрану HID
   - Audi `/info hidDevices[].uuid` имеет значение **String** "0"/"1"(touch=uuid 1 eso_touchScreen,
     Сообщение 5 байт `[tip 1bit][X u16LE][Y u16LE]`, верхняя граница координат 1412х654=разрешение экрана)
   - Канал событий представляет собой двусторонний RTSP: **200 будет возвращено немедленно для каждого входящего запроса**, в противном случае конвейер запросов «автомобиль-машина» будет заполнен, и канал умрет.
     (Выражается словами «Он может соскользнуть и сломаться»).
   - Канал событий `iAPSendMessage` передает **виртуальную ссылку iAP2**, инициированную транспортным средством (маркер = DETECT, один вопрос и один ответ,
     Клиент отправляет SYN в машину - сервер отправит его обратно в Detecting, если повторно отправит DETECT)
5. **Три улучшения стабильности**: номер генерации потока клиента BT (параллельная защита от зомби), регистрация ctrl mDNS и сетевая привязка.
   (Принудительная перерегистрация после смены/привязки сети, каждый раз создается прослушиватель), результаты mDNS фильтруются по сегменту автомашинной сети
   (Анти-совместное использование мобильных точек доступа использует компьютер AirPlay в качестве автомобильного устройства).
6. **Пит процесса отладки (запомните на всю жизнь)**: `adb install -r` не убивает старый процесс - старый dex продолжает работать,
   Если «восстановление недействительно», сначала перезапустите принудительную остановку; при проверке генерация процесса (количество потоков `ps -T`)
   Проверьте обе строки в APK (распаковка dex grep).

**Настоящий прорыв в автомобилестроении фазы 3 (09.10.2026, Audi_MMI_6318 / MHI3_AS_AU_P3801, см. `docs/PROTOCOL-NOTES.md` §9b)**:
По сравнению с испытательным стендом (DiPlay) Audi MIB3 имеет шесть ключевых отличий. После их поочередного исправления впервые подключилась полная ссылка iAP2:
1. Транспортное средство **активно отправляет SYN**, чтобы объявить таблицу сеансов `{1:control, 2:EA}`, и мобильный телефон должен ACK+ повторить ее как есть.
   После этого CSM принимает **Сеанс №1** (отправка №10 и машина молча отбрасывает его, но канальный уровень подтверждает как обычно - очень сбивает с толку)
2. **Запрос MFi должен составлять 20 байт** (машина 32B вообще не отвечает; вместо этого тестовый стенд DiPlay требует 32B → сделан откат 20.32.16)
3. Автомобиль **не отправляет 0x4301** (список возможностей кадра распознавания реален: 0x4e0c/0x4e09/0x4e0d/0x4e0e/0x5702/0xea00/0xea01,
   Можно отправить 0x5703/0xea03) → Конечная точка AirPlay может работать только через Wi-Fi **mDNS `_airplay._tcp`** Обнаружен
4. **Взаимная блокировка приглашения ctrl**: Автомобиль обнаружил телефоны `_carplay-ctrl._tcp` и `GET /ctrl-int/1/connect` по Wi-Fi.
   Открыть окно AirPlay после приглашения → Телефон должен быть привязан к точке доступа + Ctrl вещания сразу по приходу 0x5703
5. ctrl TXT `id` должен быть **настоящим MAC-адресом Bluetooth** (оболочка Shizuku читает `settings secure bluetooth_address`;
   API прикладного уровня имеет только заполнитель `02:00:…`, а значение заполнителя приводит к тому, что транспортное средство не приглашается → двусторонний тупик)
6. Настройка пары — **403** (Audi не принимает анонимное соединение SRP) → перейдите к быстрому пути проверки пары «сопряженное устройство»;
   И **НИКОГДА** не прерывайте сеанс управления BT (взлом отсоединения на тестовом стенде заставил бы Audi прервать весь сеанс)

**Запись об отладке реального компьютера на этапе 1 (08.10.2026, DiPlay на Redmi K40)**:
1. Общая блокировка чтения-записи `StreamDuplexStream` приводит к взаимоблокировке (чтение блокируется и блокируется, а запись ждет вечно) → разделение чтения и записи.

## Строительство испытательного стенда (инструкции для этапа 0)

1. **Резервное копирование телефона Android** (Android 9+): из [DiPlay Releases](https://github.com/shihabal3amri/DiPlay/releases)
   Скачайте APK и установите его - это наша "виртуальная машина-машина" (ресивер).
   (DiPlay является производным от xcertplay и является более активным; оба исходных кода в `reference/` зарезервированы для справки.)
2. **Сопряжение двух мобильных телефонов по Bluetooth на системном уровне** (просто соедините их непосредственно в настройках, что является необходимым условием для обратного подключения DiPlay).
3. **Установите это приложение на телефон Honor**:
   ```bash
   ./gradlew assembleDebug
   adb install app/build/outputs/apk/debug/app-debug.apk
   ```
4. Выполните четыре шага в интерфейсе:
   - **③ Запустите мониторинг Bluetooth iAP2**: отслеживайте UUID iPhone и дождитесь повторного подключения DiPlay.
     После подключения журнал будет выгружен в шестнадцатеричных байтах — см. `ff 55 02 00 …`, который представляет собой SYN канального уровня.
     Основные точки проверки Этапа 0;
   - Выберите беспроводной режим (точка доступа/LAN) для устройства резервного копирования DiPlay. После включения он просканирует сопряженный мобильный телефон и подключится обратно;
   - **① Подключение к точке доступа**: введите SSID, отображаемый на DiPlay (введите пароль во всплывающем окне системы);
   - **② Сканирование _airplay._tcp**: необходимо проанализировать конечную точку AirPlay + TXT (deviceid/features/pi/pk) резервного компьютера;
   - **④ Трансляция _carplay-ctrl._tcp**: убедитесь, что DiPlay может обнаружить канал управления мобильным телефоном и снова подключиться к нему.
5. Релизная версия DiPlay имеет встроенные экспериментальные идентификаторы аксессуаров, извлеченные из прошивки Carlinkit (как указано в README),
   Вы можете пройти аутентификацию MFi (наш отправитель пропускает проверку). Если вам необходимо иметь с собой собственный идентификатор MFi (чип/локальный сертификат/
   Три способа удаленного обслуживания), см. README xcertplay.

## Качество кода (автоматически перехватывается перед отправкой)

Отправить（`git commit`）раньше pre-commit крючок（`.githooks/pre-commit`，по `core.hooksPath` включить）
Два шага будут выполнены автоматически，Любая неудача препятствует отправке：

1. **Форматирование кода**: Spotless + ktlint (официальный стиль кода Kotlin, правила в корневом каталоге `.editorconfig`).
   Временно сохраненные `.kt`/`.kts` будут автоматически отформатированы и переустановлены без ручной обработки;
2. **Android Lint**: `lintDebug` полностью проверен, проблемы на уровне ошибок привели к сбою отправки.

Ручная команда:

```bash
./gradlew SpotlessApply # Полный формат
./gradlew :app:lintDebug # проверка ворса (отчет: app/build/reports/lint-results-debug.html)
./gradlew :app:updateLintBaseline # Перестройте базовый уровень lint после устранения проблемы
```

Существующие проблемы с ворсом (273 элемента, все они выбраны намеренно в сценариях автомобильного пользовательского интерфейса: жестко закодированный китайский копирайтинг, позиционирование в пикселях, RTL и т. д.)
Запись исключена из `app/lint-baseline.xml`; **Новый код, вызывающий аналогичные проблемы, по-прежнему будет блокироваться**.
Как только проблема будет фактически устранена, базовая запись автоматически станет недействительной; если подтверждено ложное срабатывание, соответствующий идентификатор проблемы может быть закрыт индивидуально или базовый уровень может быть перестроен после проверки.
После нового клона вам нужно один раз выполнить `git config core.hooksPath .githooks`, чтобы включить перехват.

## Сборка и публикация

```bash
./gradlew :app:assembleDebug # Пакет ежедневной отладки (app/build/outputs/apk/debug/)
./gradlew :app:assembleRelease # Пакет выпуска (app/build/outputs/apk/release/)
./gradlew testDebugUnitTest # модульный тест
```

**Номер версии**: `app/build.gradle.kts` Вверх `appVersionName` — единственный источник (семантическая версия),
`versionCode` автоматически получается из него (`major*10000 + minor*100 + patch`), чтобы избежать рассинхронизации двух мест.
Пользователи не могут устанавливать обновления без какого-либо запроса. Меняйте эту строку только при смене версии.

**CI автоматически выводит пакет** (`.github/workflows/android-ci.yml`): при каждой отправке используются секреты из хранилища.
Официальное хранилище ключей сборки `assembleRelease` и автоматическое накопление номера сборки — пройти
`-Pcardeck.buildNumber=<run_number>`, получаем `0.1.13.<N>`/`versionCode=base*10000+N`
(+1 за каждое нажатие, вы можете напрямую перезаписать и установить предыдущую версию; она автоматически заменится при обновлении патча). продукт
`CarDeck-<версия>-release.apk` присутствует только в Артефактах действий и **не публикует выпуск GitHub**.
Если нет `KEYSTORE_BASE64` (и `KEYSTORE_PASSWORD` / `KEY_ALIAS` / `KEY_PASSWORD`)
Конвейер выходит из строя напрямую, и «официальная версия» с отладочными сигнатурами не будет создана.

**Сигнатура**: локальный `assembleRelease` возвращается к исходному состоянию, когда нет `keystore.properties` **подписи отладки**
(Только для форкеров для пробной установки; сборки CI с номерами сборок будут напрямую сообщать об ошибках). Пожалуйста, настройте настоящую подпись перед официальным распространением:

1. Скопируйте `keystore.properties.example` → `keystore.properties` (gitignore);
2. `keytool -genkeypair -v -keystore cardeck-release.jks -alias cardeck -keyalg RSA -keysize 4096 -validity 10000`；
3. После ввода пароля снова введите `assembleRelease` и используйте `apksigner verify --print-certs`, чтобы подтвердить, что CN сертификата не `Android Debug`.

> ⚠️ Утечка закрытого ключа = любой может выпускать обновления, которые могут перезаписать установку; закрытый ключ утерян = установленные пользователи больше не могут получать обновления
> (Только позволяет всем удалять и переустанавливать). Хранилище ключей и пароль никогда не сохраняются в базе данных и не отправляются.

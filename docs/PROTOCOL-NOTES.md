# Примечания к протоколу беспроводной передачи данных CarPlay

> Цель этого проекта: телефон Android действует как iPhone (отправитель CarPlay) и подключается к автомобильному устройству CarPlay (приемнику).
> Эта заметка объединяет четыре локальных справочных склада (`reference/`: DiPlay, xcertplay, catplay,
> carplay-wifi-extractor, gitignore) и общедоступный обратный сбор данных.
> **Приемник на испытательном стенде фактически использует DiPlay** (производная от xcertplay, `reference/DiPlay/`);
> Путь чтения с интенсивным использованием кода — это в основном xcertplay (`reference/xcertplay/`). Два исходных кода имеют один и тот же источник, и логика протокола согласована.
> Те, что отмечены знаком ✅, были подтверждены построчно в ссылочном коде; те, которые отмечены ❓, — это элементы, которые необходимо проверить.

## 1. Роль и модель аутентификации

| | Ресивер (роль автомобиля) | Отправитель (роль iPhone, этот проект) |
|---|---|---|
| Проведено | Audi Car Machine / DiPlay (испытательный стенд) | Это приложение |
| Требуется удостоверение личности с подписью Apple | ✅ Да (сертификат/чип MFi, проверено по телефону) | ❌ Нет |
| Подтвердите личность другой стороны | ❌ Нет (односторонняя аутентификация, подтвержденная Oligo DEF CON 2025) | Опционально (непосредственно пропустить этап испытательного стенда) |

**Основной вывод**: аутентификация iAP2 является односторонней: мобильный телефон проверяет учетные данные MFi автомобиля (ответ на вызов сегмента 0xAA00),
Автомобиль-машина полностью доверяет результатам проверки, сообщаемым мобильным телефоном. Поэтому отправителю не нужны никакие материалы для подписи Apple.
Сертификат, который DiPlay извлекает из прошивки Carlinkit, бесполезен для отправителя (это идентификатор получателя).

## 2. Иерархическая структура (снизу вверх)

```
┌────────────────────────────────────────────────────────┐
│ Основной сеанс AirPlay: управление стилем RTSP + потоковая передача H.264/H.265 + HID │ Фаза 2
│ Носитель: WiFi TCP (автомобильный порт AirPlay, от 0x4301) │
├────────────────────────────────────────────────────────┤
│ mDNS/Bonjour: автомобильная трансляция _airplay._tcp; трансляция мобильного телефона │
│ _carplay-ctrl._tcp (к этому порту подключена машина) │
├────────────────────────────────────────────────────────┤
│ Сеанс управления iAP2 (CSM): кадрирование 0x4040 + тело параметра TLV │ Фаза 1
├────────────────────────────────────────────────────────┤
│ Канальный уровень iAP2: кадр данных FF55 SYN / FF5A + контрольная сумма │ Фаза 1
│ Носитель: Bluetooth RFCOMM (беспроводной)/USB-массив (проводной, за исключением) │
└────────────────────────────────────────────────────────┘
```

## 3. Слой ссылок ( ✅Исправлено xcertplay Iap2LinkEngine.kt, 08.10.2026)

Заголовок кадра данных (обратный порядок байтов, 9 байт + полезные данные + контрольная сумма полезных данных):

```
ФФ 5А | u16 общая длина | u8 контроль | u8 сек | u8 акк | идентификатор сеанса u8 | контрольная сумма заголовка u8 | полезная нагрузка | контрольная сумма полезной нагрузки u8
```

**Фактическая коррекция измерений на этапе 1 (отличия от предыдущих примечаний)**:
- Рукопожатие не является «кадром управления FF55»: обе стороны отправляют друг другу маркер `FF 55 02 00 EE 10`, а затем отправляют пакет синхронизации.
  (Кадр FF5A, управление = 0x80, полезная нагрузка = структура согласования параметров `>BBHHHBB` + дескриптор сеанса × 3)
- **В беспроводном режиме инициатором синхронизации является мобильный телефон**: аксессуары (openWireless, ignoreNegotiation=false)
  Отправьте только маркер и подождите, пока мобильный телефон сначала отправит пакет синхронизации; обе стороны вернут ACK после получения пакета синхронизации и перейдут в режим NORMAL после получения ACK в состоянии согласования.
- **Идентификатор сеанса – 10 (Управление)/11 (EA)/12 (Передача файлов)**, а не 0/1/2, как в примечаниях Олиго.
  (Это может быть вариант носителя Bluetooth; при условии совместимости DiPlay с 11 октября 2012 г.)
- Серийный номер u8 заворачивается, начальный 99; управление кадром данных = 0x40 (с ACK)
- Биты управления: SYNC=0x80, ACK=0x40, EAK=0x20, RST=0x10.
- Контрольная сумма = дополнение суммы байтов (модуль 256 == 0, включая контрольную сумму), по одному для заголовка/полезной нагрузки.
- Справочник параметров беспроводной сети (DiPlay/xcertplay WIRELESS_LINK_CONFIG): maxOutgoing=4,
  controlSessionVersion=2, сохранить ACK (проводной режим нулевого подтверждения)
- Большой кадр CSM фрагментируется в соответствии с максимальной длиной, согласованной партнером, а принимающая сторона повторно собирается анализатором CSM.

**Код этого проекта**: `app/src/main/java/.../iap2/Iap2LinkEngine.kt` (полный конечный автомат, протестирован с помощью обратной связи)

## 5. Беспроводное управление таймингом ( ✅ xcertplay `Iap2WirelessControlClient.kt` + экстрактор README)

После установления соединения Bluetooth RFCOMM (сначала необходимо выполнить сопряжение двух устройств на системном уровне):

```
Аксессуары → Мобильный телефон: FF55 SYN (Кто инициирует рукопожатие канального уровня ❓ Проверка фазы 1)
Мобильный телефон → Аксессуары: StartIdentification (0x1D00)
Аксессуары → Мобильный телефон: IdentificationInformation (0x1D01) Идентификация автомобиля + Список возможностей отправки и получения сообщений
Мобильный → Аксессуары: Идентификация принята (0x1D02)
Аксессуары → Мобильный телефон: Последовательность сертификации MFi (раздел 0xAA00) ← Верификацию можно пропустить на стороне мобильного телефона ❓Подробнее прочитать
Мобильные устройства → Аксессуары: RequestAccessoryWiFiConfiguration (0x5702) ← **Требуется**: Четыре независимых
                                                   Реализация декларирует это; также необходимо выдать декларацию об утечке двигателя.
                                                   (См. §5b / §9j)
Аксессуар → Мобильный телефон: AccessoryWiFiConfiguration (0x5703) TLV в виде обычного текста: SSID/пароль/канал/тип безопасности
   (Тип безопасности: 0=Нет 1=WEP 2=WPA/WPA2 3=WPA3 Переходный 4=WPA3)
Мобильный телефон подключается к автомобильной точке доступа → анализ mDNS _airplay._tcp
Мобильный телефон → Аксессуары: CarPlayAvailability (0x4300)
Аксессуары → Мобильный телефон: CarPlayStartSession (0x4301) Параметры беспроводной связи + Автомобильный IP + Порт AirPlay
                                                    + идентификатор устройства + открытый ключ + исходная версия
Телефон → Аксессуары: WirelessCarPlayUpdate (0x4E0D) уведомляет о доступности беспроводного CarPlay.
Мобильный телефон → Аксессуар: DeviceTransportIdentifier(0x4E0E) Идентификация Bluetooth/USB, аксессуар будет отправлен повторно после получения 0x5703
Аксессуары → Мобильные телефоны: StartHID (0x6800) Фаза 2: Touch Return Channel
Мобильный → Аксессуары: DeviceHIDReport (0x6801) Ответ
```

0x1D01 Расположение параметров удостоверения (отправителю необходимо разобрать; идентификатор поля → значение):
0=имя, 1=идентификатор модели, 2=производитель, 3=серийный номер, 4=версия прошивки,
5=версия оборудования, 6=список идентификаторов отправленных сообщений (u16[]), 7=список идентификаторов полученных сообщений (u16[]),
8=Тип источника питания, 9=Максимальный ток (мА), 10=Группа протоколов ЕА, 12=Язык, 13=Список языков,
16=компонент передачи USB (проводной), 17=компонент передачи Bluetooth (беспроводной), 18=компонент HID, 24=компонент беспроводной связи CarPlay (включая SSID).

## 5б. 0x5702 — «необходимое, но часто упускаемое утверждение» — внешнее свидетельство четырех независимых реализаций (22 октября 2026 г.).

Причина: 0.1.13 Изменение с «можно подключиться» на «невозможно подключиться» на Audi MMI 3315. 8b64147 Введите учетные данные WiFi
Назначение записывается как «Если в списке дебиторской задолженности нет 0x5702, старый протокол будет пропущен», а разреженный список Audi (отправить 2 элемента/
Получите 5 предметов) в комплект не входит. В результате 0x5702 не был отправлен ни разу за весь раунд, а сервис AirPlay на автомобиле так и не запустился.
(Порт 7000 повсюду ECONNREFUSED), 4 раунда сеансов, самоуничтожение по 8 секунд каждый.

**Все четыре независимых реализации включают 0x5702 в список «приемлемых автомобилей и машин»**, что указывает на то, что это обязательный элемент, требуемый спецификацией:

| Проект | Роль | Расположение доказательств |
|---|---|---|
| кошачья игра | автомобильная машина (приёмный гаджет) | `catplay_carplay_rx_gadget/src/iap2_session.rs`: `(identity.wifi_ssid.is_some(), &[RequestAccessoryWiFiConfigurationInformation::PACKET_ID])` |
| xcertplay | Автомобильная машина | `Iap2IdentificationClient.kt:315`: `WIRELESS_PHONE_MESSAGES = intArrayOf(0x4e0d, 0x4e0e, 0x5702)` |
| аминеросс/витрина | Автомобиль-машина (разлоченный iPhone) | `source/carplay_bt.m` из `msgs_recv[]`, включая `0x5702 /* RequestAccessoryWiFiConfigInfo */` |
| виомок/iap2 | Автомобиль-машина (Питон) | `msgs_recv` `iap2/__main__.py` включает `RequestAccessoryWiFiConfigurationInformation` |

**Следствие**: отсутствие 0x5702 может означать только «список неполный», но не может опровергать «не поддерживается». Реальные автомобили часто пропускают надпись
(Audi MMI 3315 есть), а необъявленные сообщения они обрабатывают как обычно - `0x4e0d/0x4e0b/0x4e0e` в журнале того же дня
Трех элементов нет в списке, а автомобиль и машина подтверждают поочередно (seq 107→ack=107, 110→ack=110, 113→ack=113).

Текущее распределение распознает только `ReceiverProfile.wifiGen`: `NEW` (сумма двух списков составляет ≥10 элементов, и 0x57xx по-прежнему отсутствует.
0x5702 пропускается, только если BMW iD9 имеет форму BMW iD9; Оба `LEGACY` и `UNKNOWN` отправляются, а окно ожидания составляет 1,5 секунды.
(Измеренная реакция восьмиколесной Audi 122/136/166/166/198/246/266/368 мс).

### Два времени отправки 0x5703 (до/после уведомления о передаче)

`amineross/showcase` и `send_accessory_wifi_config(phase)` различают пре-/посттранспорт:
`mfi_auth_succeeded → wireless_carplay_connecting_seen → Transport_notification_seen
→ wifi_config_sent_post_transport` (повторно отправить до 5 раз). Его комментарии документируют контрпример:

> На iPhone8,1 / iOS 15.8.3 партнер запрашивает конфигурацию Wi-Fi **до** 0x4E0E, поэтому сначала отправляется старый код
> 0x4301, а затем сетевая фаза больше никогда не запускалась.

То есть сама по себе последовательность не обязательно является фатальной (0x5703 в нашем журнале Audi на 19/10-20 раньше, чем 0x4e0d/0x4e0e
Прибытие, как обычно, прошло успешно), но чувствительность к времени реальна. Наш механизм проверки активности повторно ответит на повторно выданный код 0x5702.
(кэш `wifi` `Iap2SenderSession`), что соответствует семантике повторной передачи витрины.

### Два потока обнаружения конечных точек (официальная версия Apple)

`docs/research/mhi2-native-wireless-2026-10/ автор `harman-f/mhi2_altscreen_carplay`
11_CONNECTION_FLOW_VARIANTS.md` объединяет два набора дизайнов Apple:

```
А. Классическая потоковая передача (WWDC 2017):
   Сопряжение → BT iAP2 (идентификация + MFi + транспортная идентификация) → Обмен учетными данными → Ассоциация WLAN
   → Просмотр/решение Bonjour → Подключение контроллера → Сеанс → Передача обслуживания iAP2 → АКТИВНО

Б. Упрощенная потоковая передача (WWDC 2023, iOS 14+):
   Непосредственный обмен конечной точкой IP + TCP-портом в iAP2 → Непосредственное установление сеанса → Безопасность + передача обслуживания транспорта → АКТИВНО
   (**Bonjour не требуется**, поддерживает только WPA3)
```

В том же документе содержится явное предупреждение Apple: **После подключения Wi-Fi и до того, как передача обслуживания CarPlay/iAP достигнет ожидаемого состояния,
Bluetooth/iAP2 нельзя разобрать**. Это теоретическая основа «8 секунд самоуничтожения за раунд = никогда не ждать приглашения» ——
В реальной записи iPhone потребовалось около 21 секунды после подключения автомобиля к сети, чтобы отправить `StartSessionHost`.

Соответствующая реализация: TXT `features=0x4040280,0x61` Audi MMI 3315 (бит37 CARPLAY_CONTROL
(оба бита 38 HK_PAIRING установлены), `srcvers=450.14.2` и фактически смешивает A (mDNS) + B (0x4301).

### Контрпример, относящийся к iOS 18 (неприменимо к Audi, но имейте в виду)

`amineross/showcase` намеренно **не объявляет** 0x4301, в комментарии объясняется почему:

> iPhone 16 Pro/iOS 18 отклоняет идентификацию, если в msgs_sent есть 0x4301.
> И 0x4300 нельзя добавить в msgs_recv — проверка iPhone 0x4300/0x4301 — это принудительное сопряжение,
> Отклонить, если 0x4301 отсутствует. Таким образом, весь путь 0x43xx заблокирован в iOS 18+.

На Audi это ограничение не распространяется: в ее списке поставки явно стоит `0x4301` (лог `Car Machine Delivery List (2)=0x4301 0xea03`).
**Вместо этого он готов объявить 0x4301, но исключить 0x5702**, что еще раз указывает на то, что список неполный и не ограничен в возможностях.
При изменении этого связанного кода не принимайте «ограничения iOS 18» витрины как общее правило для всех автомобилей.

## 6. mDNS/Bonjour（ ✅ xcertplay `network/CarPlayBonjour.kt`）

**Со стороны автомобиля** Трансляция `_airplay._tcp`, запись TXT:

```
deviceid=AA:BB:CC:DD:EE:FF   features=0x44540380,0x61   flags=0x4
model=...  srcvers=...  protovers=1.1
pi=<идентификатор сопряжения> pk=<шестнадцатеричный открытый ключ ed25519>
```

**Сторона местного телефона** передает `_carplay-ctrl._tcp` (TXT: `id=<Bluetooth MAC>`), автоматический компьютер разрешает и **меняет соединение** с портом.
Служит каналом управления (т. е. оператором связи, через который сеансы управления iAP2 переносятся с Bluetooth на Wi-Fi TCP).
Тестовый стенд (DiPlay, унаследованный от xcertplay) предпочитает локальный IPv6, возвращается к IPv4 — измеренное обнаружение ctrl
Исходный адрес — `fe80::…%wlan0`.

## 7. Bluetooth RFCOMM ( ✅ xcertplay `CarPlayController.kt:1591,1963`)

- iPhone (отправитель) отслеживает службу SDP: UUID `00000000-deca-fade-deca-deafdecacafe`
- UUID на конце аксессуара: `00000000-deca-fade-deca-deafdecacaff`
- Стратегия подключения испытательного стенда (DiPlay): сканирование **парных** устройств `PHONE_SMART` → подключите указанные выше UUID один за другим.
- Таким образом, испытательный стенд требует только: сопряжения двух мобильных телефонов на системном уровне → мониторинг с помощью этого приложения → резервное соединение DiPlay.

## 8. Основной сеанс AirPlay (этап 2, только индекс)

- Эталонная реализация: catplay `carplay/catplay_carplay/src/carplay_tx/` (линия отправителя 1959) +
  `screen/tx/` (сеанс отправки видео) + `rtp/record/` (RTP передающей стороны) + `pairing/pairing_helper_tx.rs`
- Шифрование: ed25519 PairSetup/PairVerify (стиль HomeKit) + RTP AES/ChaCha.
  (Эталонная реализация принимающей стороны находится в xcertplay/DiPlay `airplay/PairSetup.kt`/`PairVerify.kt`/`Srp6a.kt`)
- Видео: H.264/H.265, преобразование инкапсуляции AVCC/AnnexB (catplay `video/`)
- Часы: порт синхронизации в стиле NTP + RTCP (catplay `clock/`)
- ❓ Не существует общедоступных спецификаций для деталей шифрования FairPlay/потока, для сравнения используется исходный код catplay + прошивка для дешифрования ludwig-v.

## 8б. Аудиоканал ( ✅Реализовано: мобильный телефон → основной аудиопоток автомобиля)

**Переговоры**: `SETUP` в зашифрованном сеансе RTSP, body = `streams:[{type:100(основной звук),
streamConnectionID, audioFormat:<bitmap>, audioType:"media"}]`;ответ получателя
`{type:100, dataPort:<UDP>, controlPort:<UDP>, streamConnectionID}`.
- Растровый формат аудио (catplay `msg/streams.rs` AudioFormat): стерео PCM 48k = `1<<15`,
  Стерео AAC-LC 48k = `1<<23`; текущая реализация использует стерео PCM 48k (базовый уровень протокола)
- Ключ потока имеет те же правила, что и видео: `HKDF(shared, "DataStream-Salt<audio connId>", "DataStream-Output-Encryption-Key")`.
— Идентификатор аудиопотока независим (используйте собственный connId) и не влияет на видео.

**Формат проводного соединения** (RTP через UDP; путь расшифровки DiPlay `AudioStream.kt` принимающей стороны подтвержден):
```
[RTP-заголовок 12B][зашифрованный текст ChaCha20-Poly1305 + тег 16B][8B nonce с прямым порядком байтов]
```

## 9д. Запись фактических измерений WinPlay (приемник Windows) (19 октября 2026 г.)

WinPlay — это беспроводной приемник CarPlay для Windows с открытым исходным кодом (`reference/WinPlay`, GPL-3.0, Node + TS,
роль получателя). Пользователь использует Honor в качестве отправителя для подключения к нему (лог `logs/cardeck/xiaomi-winplay.log`):
iAP2 → WiFi → mDNS → сопряжение всех, зависло на уровне НАСТРОЙКИ уровня сеанса.

**Основная причина: `deviceID` SETUP на уровне сеанса должен быть равен MAC-адресу Bluetooth iPhone, выбранного принимающей стороной.**

- WinPlay начинается с `cfg.targetBluetooth` (выбранный пользователем сопряженный iPhone в Windows)
  Установить фильтр: `stack.deviceFilter = id => normalize(id) === normalize(cfg.targetBluetooth)`
  (`reference/WinPlay/src/engine/run.ts:64`).
- Если `dict.deviceID` не совпадает (или поля отсутствуют) в SETUP на уровне сеанса, **403** будет возвращено напрямую.
  (`src/engine/protocol/cpStack.ts:696-699`); `RECORD` также 403 до приемки оборудования.
- То, что мы выпустили ранее, было жестко запрограммированным поддельным значением Catplay `ff:ee:dd:cc:bb:aa`.
  (Старый комментарий «Автомобиль и машина не откалиброваны» справедлив только для Audi/DiPlay).
- строка состояния `RTSP/1.0 403 OK` является отпечатком WinPlay: в ее таблице `STATUS_TEXT` нет записи 403,
  `buildResponse` возвращается к `OK` (`src/engine/protocol/rtspMessage.ts`). См. «403 ОК».
  Отдавайте приоритет подозрениям в фильтрации устройств, а не общим различиям в реализации RTSP.
- Симптом после сбоя - "автоматическое отключение примерно через 45 секунд после подключения": отправитель больше не отправляет запросы, а у получателя истекает время ожидания видео.
  (`armVideoDeadline` 45s), а затем удалите ссылку. Отправитель должен активно закрываться, когда SETUP не равен 200, и не ждать молча.

В отличие от Audi/DiPlay: оба не проверяют идентификатор устройства SETUP, поэтому это поле долгое время не было обнаружено.
Этот проект был изменен для повторного использования **настоящего собственного MAC-адреса Bluetooth**, проанализированного `DeviceIdentity` (аналогично 0x4300/0x4E0E).
Согласовано), значение-заполнитель `02:00:00:00:00:00` используется только тогда, когда Шизуку не готов, и включается в журнал 403.
Четко подскажите «получающая сторона, пожалуйста, выберите этот адрес».

**Другие возможности WinPlay (полезные для этого проекта)**:

- Исправлен порт TCP 17000; `_airplay._tcp` TXT такой же, как iPhone.

  Ключ потока также получается в соответствии с `DataStream-Salt<id>`, который можно использовать в качестве третьей перекрестной проверки поведения принимающей стороны.

**Кстати, исправлена ​​ошибка кодирования bplist**: `BinaryPlist.encodeInt` изначально выбирал ширину в соответствии с **беззнаковым** диапазоном.

-30087. Временные порты (timingPort/eventPort/dataPort часто относятся к номерам 32768..65535) будут задействованы;
WinPlay использует беззнаковое чтение BigInt, поэтому на него это не влияет. Пострадает ли Audi, неизвестно (видео было нормальным, но не
Исключите его из игнорирования неправильного тайминг-порта). Теперь ширина выбирается согласно диапазону со знаком `Byte/Short/Int`.

**Основная причина номер один: SYN-ACK повторно использует порядковый номер SYN.** Необработанные байты:

```
Наш SYN: ff 5a 00 1d 80 63...seq = 0x63 (99)
Наш SYN|ACK: ff 5a 00 1a c0 63 a1 ... seq = 0x63 (99) ← Коллизия чисел
```

`sentSequence` увеличивается только тогда, когда `drainSendWindow()` отправляет кадры данных, и никогда не увеличивается во время фазы согласования. Нажмите на противоположный конец
Пакет проверки `SYN.seq + 1` (кошачья игра `verify_neg_seq_ack`: `packet.seq == peer_seq + 1`),
Дубликаты кадров с одинаковым порядковым номером отбрасываются. `NegotiationTx::SynAck` Catplay увеличивается на `take_own_seq()`.
Исправлено: `sendSynchronizationEcho` использует новый порядковый номер; **Повторные передачи одного и того же SYN на уровне байтов остаются идемпотентными**
(Воспроизводится предыдущий кадр без увеличения порядкового номера — туннельный режим DiPlay повторно передает один и тот же сигнал SYN каждые 500 мс).

**Основная причина вторая: только первый SYN получает SYN|ACK.** Старая реализация `if (firstAdoption) sendSynchronizationEcho(...)`,
Каждый последующий SYN возвращает только голый ACK. И BMW **возобновляет переговоры с новым серийным номером** (161→191→40...,
В журнале за один раунд принимается максимум 36 SYN), и вы никогда не сможете дождаться желаемого эха. кошачьи игры `on_recv_neg_host`
Отправьте SYN+ACK для каждого SYN. Исправлено: **Каждый чистый SYN (без бита ACK) возвращает один кадр SYN|ACK**.

**Ошибка: «Голый» ACK будет конфликтовать с SYN|ACK.** «Голый» ACK использует текущий `sentSequence`, а значение SYN|ACK будет увеличиваться автоматически.
Следующий голый ACK будет повторно использовать порядковый номер предыдущего кадра SYN|ACK. Поэтому путь к хосту изменяется на **возвращается только SYN|ACK** (он поставляется с
Бит и поле подтверждения ACK, голый ACK по своей сути избыточен; путь хоста catplay отправляет только SYN+ACK).
Стоимость: последовательность кадров «голый ACK + SYN|ACK», измеренная Audi, заменяется на один кадр SYN|ACK – все еще в соответствии с протоколом,
Однако необходимо провести повторную проверку и подтвердить на Audi (окончательный ACK вернет 100 вместо 99, и смещение серийного номера на один бит является нормальным).

**Ошибка: SYN|ACK не может быть возвращен для всех кадров с битом SYN.** Первая версия реализации не различала SYN и SYN|ACK.
Когда два двигателя питают друг друга, образуется бесконечный пинг-понг (одиночный тест `windowBacklogFlushesAfterAcknowledgement` напрямую
Он зависает и простаивает процессор на 55 секунд, прежде чем `jstack` его увидит). Критерий должен быть `control and ACK == 0`.

| Шлюз `:7000` | 54-е Все `ECONNREFUSED` | Подключитесь немедленно |

**Основная причина: TXT `srcvers` и имя экземпляра, транслируемое с помощью ctrl, были изменены мной, нажав catplay.** 0.1.6 Да
`name=sender` + `srcvers=950.7.1` (распознавание автомобилей и машин); 0.1.7 изменен на `name=iPhone`+
Для `srcvers=566.25.21` (версия SDK передатчика Catplay) автомобиль и машина больше даже не обнаруживают.
Эти два элемента являются единственными идентификаторами телефона, которые автомобиль может видеть по Wi-Fi, и их изменение эквивалентно смене устройства.
→ Откатился на значение 0.1.6 и добавлен тест `CarPlayCtrlAdvertiserTest` для его закрепления (больше в дальнейшем не использовать)
«Копия из кошачьих игр»).

**Также удалите трансляцию `_device-info._tcp`**: `NsdServiceInfo` для Android не принимает порт=0,
Реальная машина каждый раз сообщает `The port is missing` (регистрация 4 раза). Это дополнительная трансляция непроверенного заработка,
Неисправность просто создает шум — устраните ее, а не исправьте, потому что нет никаких доказательств того, что она нужна машине.

**Кстати, еще две проблемы, которые необходимо устранить**:

1. **0x4300/0x4E0E использует заполнитель MAC**: полный журнал этой статьи.
   `Приветствие о состоянии устройства … mac=02:00:00:00:00:00`. `DeviceIdentity` имеет 10 секунд молчания при сбое синтаксического анализа
   окно, и сессия BT часто создается в ту же миллисекунду, когда Шизуку готова - все возвращается в течение 10 секунд после первого сбоя
   Значение заполнителя (второй и третий раунды в журнале 0.1.6 — это настоящий MAC `5C:40:71:A4:0A:90`). Ауди примет это
   Идентификатор передачи 0x4300 проверяется по одноранговому узлу RFCOMM, а значение-заполнитель вызывает автоматическое отбрасывание.
   → `BtSession` заменяется на `forceRetry` для анализа и регистрации при запуске сеанса.
2. **Трансляция TXT по ctrl никогда не вносилась в журнал**: В результате вышеизложенное нельзя напрямую отнести (можно полагаться только на сравнение версий).
   → Каждый раз, когда при регистрации печатается `name= / id= / srcvers=`, заполнитель MAC дополнительно помечается ⚠.
3. **Никаких объявлений не будет, и mDNS больше не будет проверяться в течение периода действия скидки**: по истечении 4-секундного окна приглашения он будет бездействовать на шлюзе только в течение 54 секунд.
   → `AirPlayClient` увеличивает `retryTick` (каждые 10 повторов ≈ 20 с): re-force_announce
   ctrl, и в лог пишем "количество авто-машинных приглашений + найден ли mDNS".

**Методологический урок**: переместите «эталонное значение реализации» непосредственно в Интернет, а цена может заключаться в том, что целый ряд реальных автомобилей будет недоступен.
Любые поля, которые влияют на то, как **автомобиль распознает наш** (TXT, имя службы, sourceVersion, идентификатор устройства),
Сначала все должно быть проверено A/B на реальном автомобиле, а изменения должны быть сразу же понятны из журналов.

## 9дж. BMW iD8.5 (MGU-86) удалил ссылку 5.4с после удаления 0x5702: приветственное сообщение было отправлено с опозданием (23 октября 2026 г.)

Лог `F:\Downloads\CarDeck-log-20261021-202434.txt` (**Пользователь дал две копии, SHA-256 абсолютно одинаковый**;

**Вид**: Все 6 раундов сеансов завершились сбоем, и поочередно появлялись два отчета об ошибках——
`СЕССИЯ не удалась: невозможно получить учетные данные автомобильной точки доступа...` и `СЕССИЯ не удалась: канал iAP2 закрыт при отправке 0x4e0d`.

**Подключено** (устанавливается в каждом раунде): RFCOMM активно подключается к **машине** (наш исходящий `BT-C` выходит из строя каждые 3 секунды) →
Ссылка Согласование SYN/SYN|ACK → Идентификация `0x1D01` (BMW Group/CinemoHIDComponent) → MFi
(сертификат `0xAA01` 611B, вызов `0xAA02` 32B, подпись `0xAA03` 68B, все возвраты проходят успешно).

**Ключевая структура: автомобиль и машина попеременно используют два профиля способностей** (почти всегда меняется один):

| Файл | Список отправки | Протокол EA | 0x5702/0x5703 |
|---|---|---|---|
| А (14 шт.) | Нет 0x5703 | Протокол `de.bmw.a4a.bt`=7 | Получить=Нет / Отправить=Нет |
| Б (16 шт.) | Содержит 0x5703, 0xaa06 | `com.bmw.carplay` протокол=8 | **Получить=Да / Отправить=Да** |

Только файл B поддерживает беспроводную связь CarPlay (а также имеет идентификационную запись `BMW 31726 Wifi`). Под файлом
Пропускаем старый протокол и переходим к 0x4300/0x4301 согласно списку возможностей - но машина не объявляет и не отправляет 0x4301, поэтому
Файл А был обречен. Что действительно следует сделать, так это B-файл.

**Мертвая точка файла B (миллисекундный график, одинаковый в обоих раундах)**:

```
T+0.9s tx 0xea00 startEASession протокол=8 com.bmw.carplay ← Автомобиль не отвечает
T+2.9s tx 0x5702 (пустое тело) ← Запрашиваем конфигурацию WiFi
T+3.0s rx link ACK (len=0) ← После этого транспортное средство не будет отправлять еще один байт
T+8.3s LINK закрыт: сокет bt закрыт, возврат чтения: -1 ← Одноранговый конец отключается
T+8.3 не удалось отправить 0x4e0d → СЕССИЯ не удалась.
```

Разница во времени стабильна и составляет 5,39–5,45 с **после** 0x5702, но не 0x5703.

**Убедительное доказательство: приветствие о состоянии устройства в беспроводном файле не было отправлено ни разу.** Полный журнал `tx=0x4e0*` появляется только в
Напильник круглый; а реальная последовательность iPhone (§12, шаг 4) — **0xAA05, а затем пакет**
`0x4E0C/0x4E0A/0x4E0B/0x4E09…`, а затем очередь подписаться/запросить. Наш код ранжирует приветствия после
`0x5703 После ожидания` (обмен WiFi в `Iap2SenderSession` → приветствие → 0x4300),
Итак BMW ждёт привет, а мы ждём 0x5703. Через 5 секунд машина определяет, что аксессуар не готов → отключите линк.

**Второй журнал (переизданный пользователем 2026-10-22, `CarDeck-log-20261022-135133.txt`) доказывает, что это воспроизводимо**:
`BMW 17713`/`MGU-86` (еще один iD8.5), Xiaomi 23127PN0CC/Android 16, приложение **0.1.17-отладка**.
**5 раундов сеансов → 5 раз tx 0x5702 → 0 раз rx 0x5703 → 5 раз LINK закрыта**, каждый раунд
`0x5702 → Только ссылка ACK → 5.37s Разборка задней части автомобиля RFCOMM → Не удалось отправить 0x4e0d`.
Эта машина имеет список из 16 элементов для каждого раунда (все указывают, что будет отправлен 0x5703), и в первом журнале нет чередования файлов A/B——
Это означает, что автомобиль серьезно пробовал использовать беспроводной CarPlay, просто мы не ответили в том порядке, в котором он просил.
(Кстати: 0.1.17-debug новее, чем 0.1.13 локального HEAD, что указывает на то, что сборка происходит из других ветвей/восходящих потоков, но сигнатуры ошибок совпадают.)

**Третье доказательство: машина заявила, что отправит `0xEA03` (статус сеанса советника), но не отправила его ни разу от начала до конца.**
`0x1D01` имеет `0xea03` в списке отправки и `0xea00` в списке приема, что указывает на то, что он поддерживает сеансы EA;
И тело `0xEA00`, которое мы отправили:

```
параметр 0: id=0, u8 = идентификатор протокола ← правильно
параметр 1: id=1, u16 =protocolId ← Ошибка: спецификация требует **строку имени протокола EA**
             Переводится как «com.bmw.carplay».
```

Старый код рассматривал параметр 1 как номер протокола и отправлял целое число (в журнале было напечатано `name=com.bmw.carplay`,
С просмотром логов проблем вообще нет). Автомобиль получил неверный запрос EA → Нет ответа `0xEA03` → Канал данных CarPlay
Не открыто → Отключить связь после исчерпания 8-секундного бюджета. Соглашение Audi EA также никогда не реагировало на `0xea03`, что указывает на эту ошибку.
Он всегда присутствовал во всех автомобилях, но Audi не полагается на него в своем развитии.

**Диспозиция (этот раунд изменений Audi не затронет)**:

1. Измените параметр 1 **`0xEA00` на имя протокола** (`Iap2Csm.string(1, name)`), и для завершения обнаружения потребуется 800 мс.
   `0xEA03` И ведите дневник - ответили вы или нет, видно сразу;
2. **Близко к `0xAA05` и немедленно** отправьте приветствие о состоянии устройства (реальная последовательность iPhone; первоначально поставлено в очередь после ожидания 0x5703);
3. Ожидание сегмента `0x5703`: 1,5 с еще не поступило → **Принудительно отправить приветствие повторно** (`force=true`);
4. Если письмо не пришло в течение 1,3 секунды → отправить `0x5702` повторно;
5. Затем продолжайте ждать согласно исходному окну, таймаут по-прежнему будет 0x4300/0x4301.

Общее количество приветствий по-прежнему равно «один раз за один раунд» (`greetingsSent` идемпотентен и будет отправлен повторно только после принудительного выполнения); Реакция Audi на миллисекундном уровне
0x5703, обе аварийные службы недоступны, и поведение остается неизменным.

**Не определено** (Если в следующий раз автомобиль по-прежнему выйдет из строя, проверьте по порядку):

1. Должен ли `0x5702` нести параметры (мы отправляем **пустое тело**, Audi принимает пустое тело, BMW может его не принять) ——
   Для определения номера параметра требуется реальный захват пакета iPhone;
2. Канал находится в НОРМАЛЬНОМ состоянии **нет периодической поддержки активности** (`Iap2LinkEngine` отправляет SYN только в течение периода согласования), и окно ожидания
   Если RFCOMM полностью молчит в течение 5 секунд, вызывается отсоединение незанятого канала BMW - если ① недействительно, добавьте голый ACK на 1 секунду, чтобы сохранить активность в следующем раунде;
3. Служба iAP2 нашего исходящего подключенного автомобиля `BT-C` дает сбой каждые 3 секунды (все из-за обратного соединения между автомобилем и компьютером). Выбор канала SDP заслуживает пересмотра.

Свяжите и перезапустите сеанс управления — возвращается только подтверждение связи (пустое эхо), когда MIB3 требуется около 10–12 секунд для демонтажа всей ссылки (этот склад

вниз через ~12 секунд без изображения».

**Асимметрия передачи** (критическая):
- Автомобиль → Мобильный телефон: байты ссылки передаются в `POST /command` на **канале событий** (TCP 5001), bplist.
  `{"type":"iAPSendMessage","params":{"data":<linkframe>}}`;
- Мобильный телефон → автомобиль: перейдите к `POST /command` (тот же iAPSendMessage) на **канале управления RTSP** (7000).
  Конверт, ChaCha Frame) — записано на канале событий MIB3 **не читается** (совместимо с DiPlay, несовместимо с Audi).

**Время** (реальная машина Frida):
1. После завершения экрана SETUP 200 (получение dataPort) мобильный телефон активно отправляет **один** маркер DETECT (управляемый
   канал) - ранняя передача будет сброшена при обмене SETUP; после этого маркеры транспортного средства и машины обнаруживаются и повторно передаются, игнорируясь;
2. Автомобиль и компьютер возвращают SYN (канал событий, чистый SYN с LSP) → мобильный телефон возвращает SYN|ACK (канал управления). ЛСП хочет заявить
   **Собственные** параметры: maxOutgoing=0x7F (отобразить таблицу узлов в том виде, в каком они есть = ограничьте себя небольшим окном узла,
   Пакетные сообщения будут сохраняться в очереди), maxLength поддерживает значение однорангового узла; таблица сеанса наследует значение однорангового узла (последующие версии могут быть внедрены
   передача файла 0x0C, используется для крышки приборной панели);
3. После того, как связь НОРМАЛЬНАЯ, мобильный телефон отправляет 0x1D00 → автомобиль 0x1D01 → мобильный телефон 0x1D02 + 0xAA00 →
   (Автомобильная машина 0xAA06, серийный номер аутентификации → мобильный телефон 0xAA00) → сертификат автомобильной машины 0xAA01 → мобильный телефон 0xAA02
   Вызов → Автомобиль 0xAA03 → Мобильный телефон 0xAA05 (принимаем напрямую без проверки). **Продолжительность испытания недоступна для номера версии**
   (Определяется генерацией чипа аутентификации MFi автомобиля, а не в каком-либо поле идентификатора/версии): Туннель захвачен Фридой
   Реальная машина 20В, DiPlay CARLINKIT распознает только 32В, а тот же MMI 3315 Bluetooth распознает 32В - так что туннель
   Путь подключен к `MfiLengthMemory` (ключ памяти = идентификационная строка + «туннель», независимо от канала Bluetooth), холодный запуск
   Базовый уровень 20B имеет приоритет, молча в течение 6 с/3 с, сдвиньте и повторите попытку, в случае отклонения (0xAA04) измените немедленно и отправьте 0xAA05 в полной тишине;
4. Мобильный телефон **пакетный** после 0xAA05 (перед любой подпиской на автомобиле): 0x4E0C идентификатор беспроводной сессии (случайный UUID в верхнем регистре),
   0xA100 (параметр 6 пустой), 0x4E0A язык «zh», 0x4E0B время устройства (u64 секунды + часовой пояс s16 + летнее время u8),
   0x4E09 Имя устройства «iPhone», 0xFFFA StartLocationInformation, 0xFFF0 Статус GPRMC ——
   Последние две — это побайтовые константы Фриды (компаньон `VirtualIap2Link`);
5. Ответ на подписку на автомобиль-машину: 0x5000→0x5001 NowPlaying пустое состояние (**путь к данным для текстов на приборной панели**, за которым следует
   MediaSessionsState), 0x4157→0x4158 состояние отсутствия связи, 0x4154→0x4155 нет вызова,
   0x4170→0x4171 пустой список; 0xEA02(requestAppLaunch)/0xA101(VehicleStatus)/
   **0xFFFB (выборка позиционирования PASCD ~1 Гц) связывает только ACK — канал управления закрывается после утечки ACK ~10 с для той же машины**.

**Изменения соответствия двигателей** (`iap2/Iap2LinkEngine.kt`, все тесты проводятся по одному):
- Когда инициатор получает SYN|ACK (не чистый SYN), он также принимает таблицу сеанса и повышает уровень воды заказа (только принимает, но не повторяет);
- Когда ответчик передает SYN|ACK, считается, что согласование завершено (реальная машина отправит 0x1D00, не дожидаясь ACK);
- Используйте ownSyncOf (maxOutgoing=0x7F) для эха, и окно отправки рассчитывается на основе **собственного значения оператора**.

**Справочный индекс AADisplay**: `carplay/protocol/WifiIap2Link.kt` (синхронизация + константа),
`CarPlayRtspSession.kt:642` (канал управления POST/метод записи команд), `docs/AUDI_CARPLAY_CONNECT_ANALYSIS.md`.
